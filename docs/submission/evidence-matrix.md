# Evidence Matrix — Product to Judging Criteria

TASK-015 §2. The public rules name judging "including, but not limited to, **technical execution,
innovation, and real-world value**" (see [`requirements.md`](requirements.md), requirement 6) and
publish **no weights**. So this matrix maps each named criterion to four things — an
implementation, a retrievable artefact, a moment in the demo, and the honest limit — and stops
there. **We do not score or rank ourselves**; nothing on this page is a self-assigned number.

Every file:line reference was re-checked against the tree at commit `34e4053`, 2026-09-29. The
submission pack that carries this file changes documentation only, so those references stay exact.

## 2. Innovation

| Angle | (A) Concrete implementation | (B) Evidence | (C) Demo moment | (D) Limitation / honesty note |
|---|---|---|---|---|
| The model judges; the code gates | Approval is decided by deterministic policy on top of the model's severity, not by asking the model whether it should be trusted | `analysis.py:11-18` and its two-line body; the comment states the asymmetry | 0:55–1:20 then 1:20–1:45 side by side: a `high` verdict, then a refusal that the model had no power to authorise | This is one floor on one field. It is not a general agent-safety framework. |
| A refusal is an audit event | Blocked attempts are appended before the error is raised, so the trail shows what *did not* happen and who asked | `workflow.py:184-189`; production trail `incident_analyzed → approval_requested → execution_blocked → approval_granted → execution_requested → execution_finished → verification_recorded` | 1:20–1:45: the trail line "Execution blocked by policy", actor `operator` | The trail is per-process. It is honest while running; it is not evidence after a restart. |
| Self-disclosing UI | Every stage chip carries its own status (`real` / `simulated in a lab` / `mixed: real gate, simulated action` / `not implemented yet`), and `LEARN` is labelled not implemented rather than omitted | `static/index.html:27-44`, disclosure badge `index.html:179`, `index.html:105` `SIMULATED ACTION` | 0:15–0:35: the loop strip itself is the "what is real" slide | The labels are authored strings matched to code paths, tested in `tests/test_console.py`. They are trustworthy because the test pins them, not because a screenshot says so. |
| Machine-first, not chat-first | The primary entry point is `POST /api/v1/events/ingest` with a producer-shaped payload; the console is a view onto the same workflow, not the input channel | `api.py:90-138`, `scripts/send_demo_event.py:31-45` | 0:35–0:55 | A judge-driven demo still uses the console form; the producer side is a script, not a running monitoring system. |
| No framework scaffolding | FastAPI + httpx + pydantic only; the console is three static files with no build step, no CDN, one same-origin script | `requirements.txt`, `git ls-files` (48 tracked files, no vendored code), page load scan: 1 script + 1 stylesheet, both `/static/`, no inline handler | Reproducibility shot: `docker build .` then one URL | Smallness is not a virtue by itself; it is here because the surface stays auditable in one sitting. |

## 3. Real-world value

| Claim | (A) Concrete implementation | (B) Evidence | (C) Demo moment | (D) Limitation / honesty note |
|---|---|---|---|---|
| An on-call engineer could adopt this shape | Four clicks, one URL, no login, no curl, works at 390 px | Production QA at 1440 px and 390 px, `scrollWidth − clientWidth = 0` at both, 0 JS errors | 0:00–0:15: open the URL cold and show the page answering | Unverified with real users. No pilot, no interview, no adoption data. |
| The gate matches how incidents are actually handled | `high`/`critical` always require a human; `low`/`medium` may proceed, and the state machine records who decided, when, and with what note | `approval` decision object with `decision`, `note`, `decided_at`; production approval was a human click 139.6 s after the request | 1:45–2:05 | A real on-call process needs escalation paths, sli/burn-rate context and paging. Sentinel has none of that. |
| Runs on infrastructure a small team already has | One container, one replica, three environment variables, ~246 MB | Coolify deployment live at `https://sentinel.novatechsystem.co.uk`; `docs/deployment/coolify.md` | 2:40–2:50 | Cost and rate limits of the hosted endpoint were not measured. |
| Speaks to an existing monitoring stack | `source`, `event_type`, `title`, `description`, `severity_hint`, `evidence[]` is a producer-shaped contract, and `scripts/send_demo_event.py` is a **NovaOps-compatible producer contract** | `schemas.py` `OperationalEvent`; `tests/test_ingest.py` | 0:35–0:55 | **Not wired to NovaOps in production.** NovaOps is a separate repository with no licence grant; the emitter is our stand-in, and we say so. |
| Inference latency is survivable | Read timeout `90 s` sized above the measured tail, not the median | Six live runs: 6.7–47.1 s; the UI shows real elapsed seconds rather than a fake progress percentage | 0:55–1:20 | 47 s is too slow for a paging system. It is fine for a demo, and the video says which one it is. |

## 4. What this matrix does not claim

Durable audit persistence; real remediation; LEARN or memory; NovaOps production integration;
multi-tenant or authenticated console access; high-throughput ingestion; measured model accuracy;
user testing. Each of those appears as a limitation above or in
[`claims-audit.md`](claims-audit.md), and none of them is dressed up as a criterion we met.
